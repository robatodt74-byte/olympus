# エージェントの行動品質を改善するEDD

適用: AIの指示・専門MD・Skill・検索経路・ツール運用を評価し、改訂する場合。2026-11-17のユーザー指定を運用可能な基準にしたもの。通常の短い依頼で全評価手順を実行しない。

## 目標と優先順位

要求した成果、正確性、必要な検証、権限境界を合格条件にし、その範囲で完了までの総トークンを減らす。短文化、読込削減、安いモデルへの変更自体を成果としない。ユーザー指定のモデルと実行条件を尊重する。

## 8つの評価軸

| 軸 | 求める行動 | 評価する証拠 |
|---|---|---|
| 主体性 | 目的から必要な情報を取りに行き、適合するSkill・既存テンプレを使って進める | 実際の参照・成果物・不要な確認待ちや重複作業の有無 |
| 確実性 | 対象・版・時点が合う根拠で判断する | 根拠と主張の対応、事実・仮説・未確認の区別 |
| 可能性 | 可・条件付き・不可・未確認を切り分ける | 確認結果、具体的なネック、実行条件と次の一手。不明を隠す断言は不合格 |
| 拡張性 | 一つの入口から必要な専門基準へ進み、別分野にも適用する | 複数の作業分野の結果と、無関係な基準を持ち込まない境界 |
| 透明性 | なぜその方式か、どう動き、どう確かめたかを再利用できる形で残す | 判断・仕組み・代替案・適用条件・証跡への参照。内部思考全文は不要 |
| 可読性 | 受け手が結論・根拠・必要な行動を把握できる分量にする | 指定形式、必要情報の保持、比較に適した表等。表やカードは必要時のみ |
| 節約 | 必要な検証を保ち、余分な読込・往復・再試行を減らす | 実測usageと作業結果。全工程を測れない場合は範囲と欠測を示す |
| 成長性 | 停滞や指摘の原因を仮説化し、対策を保存して次の作業で使う | フィードバック→記録→次の同種作業での参照・適用。保存だけで成功としない |

「可能性」は実行可否の判断精度を指す。「未確認」と適切に示し、確かめ方を提示する応答も合格にできる。失敗例・原因・体験を創作して成長したように見せない。

## EDDの進め方

1. 目的、対象、非対象、必要な行動、禁止事項、観測する結果を先に固定する。必要な軸だけ適用し、非該当と未観測を区別する。
2. 代表例・境界例・負の例を用意する。失敗の再利用は根拠と適用条件を確認する。実例と合成例を区別し、評価に使った例を独立した未見課題と呼ばない。
3. 現行版を同じ課題で測る。どこで失敗したか、本文・検索経路・ツール・出力形式・保存先を切り分ける。失敗が出なければ、直す理由を作らない。
4. 原因に対応する最小の一箇所を変える。プロンプトや指標の変更を同時に重ねず、条件と入力・成果物の版を残す。
5. 同じモデル・推論強度・権限・課題・採点規則で再比較する。行動は実行記録と成果物で確認し、回答に「参照した」とあるだけで加点しない。
6. 品質を確認してから消費を比べる。必要な節目では反復と独立した評価者を加える。曖昧な自動採点は元の成果物で確認する。
7. 採否と理由、適用条件、次回の確認を既存のObsidianへ残す。次の同種作業で対策を使えたかを評価へ戻す。経験の正本は[知識運用](../knowledge/operations.md)と既存のLessons Learnedを使う。

## 採点と採用

行動品質は0＝未達・誤り、1＝部分的、2＝条件を満たすで診断する。未観測を0点にせず、非該当を満点にしない。重大な捏造・権限違反・必須要件の欠落は平均点で相殺しない。タスク固有の必須条件を合否に使い、8軸の総合点だけで採用しない。

- 品質軸に退行がなく、少なくとも一軸の改善とトークン減少が観測できれば「両方の改善」とする。
- 品質が同じでトークンだけ減れば「品質維持・消費減」と報告する。
- 品質が上がって消費が増えた場合は、必要な場面と増加分を示して使い分ける。
- 欠測、少数例、単一回の結果、同じモデルによる自己評価の限界を明示する。

主体性・透明性・成長性は、一回の文章生成だけでは十分に測れない。許可した一時作業フォルダや保持する状態で、参照・成果物作成・次回の適用を確認する。検証できない項目を「実装済み・効果確認済み」としない。

## 節約と進捗共有

資料は名前・説明・索引から選び、必要な本文と節だけ読む。既存テンプレ、定型集計、取得済みで有効な根拠を再利用する。不要な一括読込・同じ調査・再実行を避ける。方法を比較するための可逆的な試行は依頼範囲で進めるが、課金・外部送信等の許可は追加しない。

ユーザー向け進捗は3〜5回の関連操作を目安に節目でまとめ、結果・不確実性・次に解く点を共有する。長い処理中は必要な更新を行い、エラー・権限不足・重要な判断待ちは即時に知らせる。固定回数を満たすための操作や、同じ状況の報告を増やさない。必要な機械ログ・証跡を3〜5回に間引く指示ではない。

## 評価費用の確認

比較は同種処理の小さな完全ペアから始める。短文試行の費用を、多段ツール作業へそのまま外挿しない。共通コンテキスト・ツール往復を含む実測usageで、次ペアの見積と残枠を確認する。残枠が不足する比較は始めず、片腕だけの試行を増やさない。

方式・範囲・予算を変える場合は新しい計画として記録し、旧版の失敗・未実施・費用を残す。試行終了後に確認する停止閾値は超過し得るため、厳密な上限と呼ばない。比較外の探索試行も評価費用へ含める。

## 記録する最小項目

課題ID、目的・必須条件、適用する軸、入力と文書版、実行条件、観測結果、失敗・欠測、入力／出力usage、修正往復、採否・理由、根拠と保存先。キャッシュ済み入力・推論出力は内数を確認し重複加算しない。測れていない親エージェントの消費や人の確認時間は欠測として残す。

通常の短い回答へ毎回チェック表・記録ファイル・カードを追加しない。常駐監視や夜間の自動書換えも本基準だけでは作らない。

日常の状況整理だけでは経験ノートを新設しない。新しい再利用可能な判断や修正の知見がある場合に、既存記録への追記を検討する。評価中の対象文書は固定し、追試や失敗の再実行は必要性と残予算を確認してから決める。
