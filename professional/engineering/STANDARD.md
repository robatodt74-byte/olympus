# 開発・Git・検証

適用: コードの設計・実装・修正・レビュー。既存プロジェクトの関連ルールを優先する。

## 設計・実装の根拠

- 公式仕様・公式ドキュメント・標準規格を基本にし、対象バージョンに合う公式推奨と、広く定着した実務上の慣行を参考に設計・実装する。AIの記憶や独自の流儀だけで決めない。
- 一般的によいとされる方法も、採用実績・保守状況・信頼できる技術資料と適用条件を確認する。人気・記事数・単一の解説を業界の合意とみなさず、公式仕様、推奨、慣行、個人の提案を区別する。
- 既存構成・要件・規模・互換性・保守性に適合する方法を選ぶ。公式サンプルは説明用の場合があるため、そのまま本番品質とは判断しない。新しさや流行だけで依存追加・移行・再設計を行わない。
- 判断に影響する仕様や不確かな用法を調べる際は[ツール選択](../tools/routing.md)に従う。対象版に適合する既読資料は再利用し、軽微な変更ごとに同じ調査を繰り返さない。
- 重要な技術選定や標準的な方法から外れる判断には、根拠・採用理由・トレードオフを必要な粒度で残す。既存ルールと公式仕様・推奨が衝突する場合は、事実と影響を確認して示す。一般論だけで既存ルールを書き換えない。
- 参照した方法が今回の要件を満たすか、最終成果物で検証する。公式資料に沿ったことだけを動作・安全性・品質の保証にしない。

## 着手と実装

- 対象リポジトリ、ブランチ、差分、未追跡、worktree、他者の作業を確認する。関連する実在のルールと仕様だけ読む。
- 受入条件と必要な検証を把握し、既存構成を使って依頼範囲を実装する。無関係な変更を混ぜず、入力・例外・権限・境界条件を影響範囲に応じて確認する。
- 最終差分を読み、呼び出し元・型・設定・文書・テストの変更漏れを確認する。並行作業は必要な場合に分離する。
- テストは実装を写すのではなく、期待する振る舞いと失敗を判定するものにする。既存のテスト基盤と必須チェックを使い、意味のない繰り返しを避ける。
- レビューは[仕事原則](../work-principles.md)に従い、第三者の視点で厳しく行う。ユーザー案・自作コードにも同じ基準を適用し、不都合な欠陥や異論を根拠・影響とともに伝える。指摘を独立して確認し、採否と理由を判断する。コード規約への適合と要件への適合は別に評価する。

## Gitの共通指定

- 操作前にブランチと差分を確認し、他者・別タスクの変更を勝手に含めない。
- pushはユーザーが希望した場合のみ、レビュー後に行う。GitHub CLIを利用する運用に従う。
- GitHub CLIの認証・PR管理と、Gitのpush転送は区別する。存在しない `gh push` コマンドを想定しない。
- commit、PR作成、merge、deployの扱いは、今回の依頼と対象リポジトリのルールで確認する。pushの許可だけでmerge・deployまで許可されたと解釈しない。
- 破壊的な操作や他者の変更の削除を、通常の片付けとして行わない。
- 並行作業がある場合は既存worktreeの状態を確認し、必要に応じて分離する。常に新規worktreeを作ることを共通要件にはしない。

## Gitと実績づくり

- Gitを作業の追跡・復元・レビューに積極的に使い、意味のある完了単位で変更をまとめる。既存リポジトリでは履歴・規約・著者設定を確認する。commitの実施は依頼とプロジェクト規則に従う。
- 継続的な成果が見えるよう、何を作ったか、使った技術、担当範囲、検証結果、動かし方をREADMEや成果説明へ必要に応じて残す。
- ユーザーは貢献履歴と扱える言語の幅を増やしたい。課題に適した言語や小さな学習・比較実装の機会を提案し、実際に動かして説明できる成果へ結び付ける。本体への不要な多言語化はしない。
- 意味のないcommit分割や表示目的だけのコード追加はしない。採用言語は要件・既存構成・保守性・学習目的で判断する。
- pushは引き続きユーザーの希望時のみレビュー後に行う。ローカルcommitを公開済みや貢献表示済みと報告しない。プロフィール表示の反映条件は必要な時点で確認する。

## Issue連携

- 開発のIssue連携はLinearとGitHub Issuesを使い、指定された対象または確立済みの運用に従う。対象未設定でも、独立して進められるローカル作業は続ける。

## 個別プロジェクト

環境開発・tsukutto・Remotionの過去例が必要な場合だけ[project-examples.md](project-examples.md)を読む。通常は対象リポジトリの現行規則を優先し、全案件の命名・運用を推測で統一しない。

## 完了条件

受入条件を満たす実装、最終変更に対応する必要な検証、残る制約の説明があること。ローカルと外部の検証、提出・受領・承認は[仕事原則](../work-principles.md)の状態区分で報告する。

認証失敗や未実施をレビュー合格にしない。
