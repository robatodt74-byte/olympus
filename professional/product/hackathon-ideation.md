# ハッカソン＆アイデア創出 ナレッジベース

出典区分: ユーザー提供の知識集を2026-11-17に見直したものです。全手法の原典照合は未完了で、確認できた一次資料は末尾に示します。人数・所要時間・回数は計画の例であり、効果を検証した数値ではありません。大会の公式規則・審査基準と今回の制約を優先します。

AIが参照するときは、索引から依頼に関係する章だけを読みます。単純な文章修正や既定仕様のバグ修正には、企画手順や本資料全文を追加しません。

## 概要

ハッカソンで成果を出すために必要な知識と、アイデアを生み出す思考法を1か所にまとめたナレッジベースです。初参加者はセクション順に、経験者は必要な章だけ拾い読みしてください。

- **参加前**：基礎知識、チームビルディングを読む
- **アイデア出しの時間**：思考法・フレームワーク集、評価・絞り込み手法を開いておく
- **開発中〜発表前**：開発・タイムマネジメント、プレゼン・デモ、チェックリストを使う

## ハッカソンの基礎知識

ハッカソンは「ハック」と「マラソン」を組み合わせた造語で、短期間（多くは1〜3日）にチームでプロダクトを企画・開発し、成果を発表するイベントです。「課題設定」「動くデモ」「実装完成度」のどれを重視するかは大会ごとに異なります。公式の審査基準と配点を確認してください。

### 主な種類

| 種類 | 特徴 | 向いている人 |
| --- | --- | --- |
| オープン型 | テーマ自由、誰でも参加可 | 自由な発想を試したい人 |
| テーマ型 | 「防災」「教育」など課題が指定される | 社会課題に関心がある人 |
| 企業・API型 | 主催企業のAPIやデータの活用が条件 | 特定技術を学びたい人、採用接点を求める人 |
| 社内ハッカソン | 社員限定、新規事業や業務改善が目的 | 部署を越えて協業したい人 |
| オンライン型 | リモートで開催、期間が長めのことも | 遠方の人、平日に進めたい人 |
| アイデアソン | 開発せず、企画のみを競う | 非エンジニア、短時間で参加したい人 |

### 一般的な流れ

1. **オープニング・テーマ発表**：主催者がテーマ、ルール、審査基準、提供技術を説明する
2. **インプット**：講演やAPI説明。審査基準はここで必ずメモする
3. **アイデア出し・チーム組成**：個人のアイデアを共有し、共感した人同士でチームを作る
4. **企画の具体化**：解決する課題、ターゲット、コア機能を決める
5. **開発**：時間配分の例は全体の6〜7割。規定の提出物、休息、統合・検証・発表準備の時間から逆算する
6. **発表準備**：スライド、デモ動画、リハーサル
7. **発表・審査**：持ち時間と質疑時間を確認する。後述の5分構成は一例
8. **表彰・懇親会**：審査員や他チームからのフィードバックを得る

### よくある審査基準

| 観点 | 審査員が見ているもの |
| --- | --- |
| 課題設定 | 誰のどんな困りごとか、それは本当に存在するか |
| 独創性 | 既存サービスとの違い、意外な組み合わせ |
| 技術力・完成度 | 実際に動くか、技術的な工夫があるか |
| インパクト | 実現したときに誰がどれだけ嬉しいか |
| テーマ適合 | 主催者のテーマや提供APIを活かしているか |
| プレゼン | 短時間で価値が伝わるか |

参加条件・必須技術・提出期限などの必須条件を満たす案を残し、審査基準の配点と残り時間から優先順位を決めます。配点をそのまま作業時間の割合にする必要はありません。

## チームビルディングと役割分担

3〜5人で役割を分担する構成は一例です。大会の人数条件に合わせ、1人なら兼任できる範囲に絞ります。開始時に担当と意思決定方法を合意し、役割の重複・不足と調整に使える時間を確認します。

### 役割の例

| 役割 | 主な責任 | 兼任しやすい役割 |
| --- | --- | --- |
| プロダクトオーナー | 課題と優先順位を決め、スコープを守る | プレゼンター |
| フロントエンド | 画面とデモで見える部分を作る | デザイナー |
| バックエンド | API、データ、外部サービス連携 | インフラ |
| デザイナー | UI、ロゴ、スライドの見た目 | フロントエンド |
| プレゼンター | 発表の構成と話し手、デモ動画 | プロダクトオーナー |

### チーム運営のコツ

- **キックオフで決めること**：目標（入賞か学びか）、使う技術、リポジトリ、連絡手段、意思決定のルール
- **意思決定は時間で区切る**：議論の上限と決定者をチームで合意する。10分などの区切りは例で、案件の重要度に合わせる
- **定期的な同期**：2〜3時間ごとに5分の進捗共有（やったこと・次にやること・困りごと）
- **非エンジニアの価値**：ユーザー調査、ストーリー作り、スライド、デモの台本は勝敗を分ける仕事
- **初対面チーム**：自己紹介で「得意なこと」「今回やりたいこと」「苦手なこと」を共有する

## アイデア創出の思考法・フレームワーク集

アイデア出しは「発散（量を出す）」と「収束（選ぶ）」を分けるのが鉄則です。このセクションは発散のための手法、次のセクションは収束のための手法をまとめています。

### 発散の基本ルール（ブレインストーミング）

アレックス・オズボーンが提唱した4原則です。

- **批判しない**：評価は後で行う
- **自由奔放**：突飛なアイデアほど歓迎する
- **質より量**：まず数を出す。1人10個が目安
- **結合・便乗**：他人のアイデアに乗って発展させる

### 手法一覧

| 手法 | やり方 | 向いている場面 | 所要時間の目安 |
| --- | --- | --- | --- |
| ブレインライティング（6-3-5法） | 6人が3案ずつ書き、5分ごとに紙を回して他人の案を発展させる | 発言しにくい初対面チーム | 30分 |
| マインドマップ | 中心にテーマを置き、連想で枝を広げる | テーマが抽象的なとき | 15〜20分 |
| SCAMPER | 既存のものに7つの問い（代用・結合・応用・修正・転用・削除・逆転）を当てる | 既存サービスの改良案を出すとき | 20分 |
| オズボーンのチェックリスト | 転用・応用・変更・拡大・縮小・代用・置換・逆転・結合の9観点で問う | SCAMPERの代替として | 20分 |
| 強制発想法（ランダム結合） | テーマとランダムな単語・技術を無理やり組み合わせる | 独創性を狙うとき | 10〜15分 |
| マンダラート | 3×3の中心にテーマ、周囲8マスに関連語を書き、さらに展開する | アイデアを網羅的に広げたいとき | 20分 |
| クレイジー8 | 紙を8分割し、8分で8案をスケッチする | UIや体験のアイデアを素早く出すとき | 8分 |
| How Might We（HMW） | 解決策を埋め込まず、課題を「どうすれば〜できるか？」の問いに言い換える | 課題からアイデアへ橋渡しするとき | 10分（短縮した問い作りの例） |
| 逆ブレスト | 「どうすれば最悪になるか」を出し、その逆を考える | 行き詰まったとき | 15分 |
| シックスハット法 | 事実・感情・批判・楽観・創造・統制の6つの立場で順に考える | 1つの案を多面的に深めるとき | 30分 |

### 課題起点の思考法

- **デザイン思考**：共感 → 問題定義 → 発想 → 試作 → テストの5段階。「共感」と「問題定義」で課題仮説を整理し、観察・利用者への確認と対応づける。審査点の上昇は保証しない
- **ペルソナとジャーニーマップ**：具体的な1人のユーザーを設定し、その人の1日や行動の流れの中で「困る瞬間」を探す
- **5 Whys（なぜなぜ分析）**：「なぜ」を重ねて原因の候補を探す。5回という回数で原因が確定するわけではないため、観測事実・仮説・未確認を分け、反例や追加の確認方法を残す
- **Jobs to be Done**：ユーザーが「片付けたい用事」は何かを考える。機能ではなく目的から発想できる
- **身近な不満リスト**：参加者自身が日常で感じる「面倒」「不便」を書き出す。実体験に基づく課題はプレゼンで説得力が出る

### 技術起点の思考法

- **提供API・データの棚卸し**：主催者が提供する技術で「何ができるか」を一覧化し、課題と掛け合わせる
- **新技術×古い課題**：生成AI、音声、位置情報などの新技術を、昔からある課題に当てる
- **異分野の転用**：ある業界の当たり前（ゲームのレベル設計、物流の追跡など）を別の業界に持ち込む

## アイデアの評価・絞り込み手法

絞り込みのゴールは「審査基準で点が取れ、かつ時間内に動くものが作れる1案」を選ぶことです。好みで選ぶと後半で崩れるため、基準を先に決めてから評価します。

### 手法一覧

| 手法 | やり方 | ポイント |
| --- | --- | --- |
| ドット投票 | 1人3票をシールや絵文字で投じる | 速い。最初のふるい分けに使う |
| インパクト×実現性マトリクス | 縦軸に効果、横軸に実装の容易さを取り、各案を配置する | 「効果大・容易」の象限を優先。「効果大・困難」は機能を削って容易側に寄せる |
| 評価シート（重み付きスコア） | 審査基準ごとに1〜5点で採点し、配点で重み付けして合計する | 大会の審査基準をそのまま評価軸にする |
| エレベーターピッチ・テスト | 30秒で説明してみる | 説明できない案は、発表でも伝わらない |
| プレモーテム | 「この案が失敗したとしたら原因は何か」を先に挙げる | 技術的リスクやデータ不足を早期に発見できる |

### 選ぶ前のチェック質問

- 誰の、どんな困りごとを解決するか、1文で言えるか
- デモで「おっ」と思わせる瞬間（ワオポイント）が1つあるか
- コア機能は残り時間の半分で作れるか
- 必要なデータやAPIは今すぐ手に入るか
- チーム全員が作りたいと思えるか

## 開発・タイムマネジメントのコツ

ハッカソンの開発は「デモで見せる一本道を、確実に動かす」ことに集中します。全機能を作るのではなく、発表で見せる操作の流れだけを完成させます。

### 時間配分の目安（24時間の場合）

| フェーズ | 時間 | 割合 |
| --- | --- | --- |
| アイデア出し・企画 | 3時間 | 約13% |
| 開発 | 15時間 | 約62% |
| 統合・バグ修正 | 3時間 | 約13% |
| 発表準備・リハーサル | 3時間 | 約12% |

### 開発の進め方

- **MVPを定義する**：MoSCoW法（Must / Should / Could / Won't）で機能を分け、Mustだけを最初に作る
- **デモの台本から逆算する**：発表で見せる画面と操作を先に紙に描き、それに必要な機能だけを作る
- **ハリボテを恐れない**：デモに不要な部分はモックや固定データで良い。ただし発表でそう明言できる範囲に留める
- **早く統合する**：各自の成果物を2〜3時間ごとにつなぎ、最後の統合で詰まるのを防ぐ
- **使い慣れた技術を選ぶ**：必須経路を成立させる最小構成を選ぶ。「新技術は1つまで」は負担を抑える目安で、必須条件ではない。得意な言語をすべて使うために構成を増やさない
- **必要な機能だけ既存手段で補う**：端末内で成立する試作には、認証・サーバー・外部DBを追加しない。それらが必須なら既存基盤やサービスを比較し、無料条件・データの取扱い・利用許可を確認する
- **機能凍結（フィーチャーフリーズ）**：統合・確認・発表準備の時間を先に確保し、新機能の追加を止める時刻を決める。終了3〜4時間前という区切りは24時間程度の大会での一例
- **デモ動画を保険として撮る**：本番でネットや環境が落ちても見せられるようにする
- **休息を取る**：徹夜は判断力を落とす。交代で仮眠を取る

## プレゼン・デモのコツ

冒頭で「誰の何を解決するか」を伝えます。デモ・説明・技術紹介の比重は、大会の審査基準と発表形式に合わせて決めてください。以下は動くデモを見せる5分発表の構成例です。

### 5分発表の構成例

1. **課題（45秒）**：具体的な1人のユーザーと、その人が困る場面をストーリーで語る
2. **解決策（30秒）**：プロダクトを1文で説明する
3. **デモ（2分）**：課題の場面がどう変わるかを、実際の操作で見せる
4. **技術・工夫（45秒）**：アーキテクチャ図と、技術的に頑張った点を1〜2個
5. **今後の展望（30秒）**：拡張性、ビジネス化、社会的インパクト
6. **締め（30秒）**：プロダクト名と1文のメッセージを繰り返す

### 伝わる発表のポイント

- **数字の根拠を示す**：効果は実測・見積もり・目標・説明用の例を区別する。「30分が3分になる」は測定していなければ実績とせず、仮説や目標と明示する。未計測なら測定方法を示す
- **1スライド1メッセージ**：文字は少なく、図や画面キャプチャを中心にする
- **デモは台本どおりに**：入力データを事前に用意し、操作手順を固定する
- **デモ失敗に備える**：録画動画、スクリーンショットのスライドを予備に持つ
- **リハーサルは最低2回**：時間を計り、超過しそうな部分を削る
- **質疑の想定問答**：「既存サービスとの違いは？」「マネタイズは？」「技術的な難しさは？」の3つは必ず準備する
- **テーマとの接続を明言する**：提供APIやテーマをどう活かしたかを一言入れる

## よくある失敗とチェックリスト

ここではスコープの広げすぎや準備不足など、確認対象にできる失敗例を挙げます。原因や頻度の順位を実証した一覧ではありません。

### アンチパターン

| 失敗 | 起きること | 対策 |
| --- | --- | --- |
| アイデア出しが長引く | 開発時間が足りなくなる | 企画フェーズに締め切りを設け、時間で決める |
| 機能を盛りすぎる | どれも中途半端でデモが動かない | MVPとデモ台本から逆算する |
| 技術ありきの企画 | 「で、誰が使うの？」と言われる | 課題とユーザーを先に1文で書く |
| 最後に統合する | 直前に動かなくなる | 2〜3時間ごとに結合して動作確認する |
| 発表準備が直前 | 時間超過、デモ失敗 | 機能凍結の時刻を決め、リハーサル時間を確保する |
| 1人に作業が集中する | ボトルネックと疲弊 | 定期同期でタスクを再分配する |
| 審査基準を見ていない | 力の入れどころがずれる | 基準をチームの見える場所に貼る |

### 参加前

- [ ] 審査基準・ルール・提出物の形式を確認した
- [ ] 開発環境、アカウント、APIキーを事前に用意した
- [ ] 使い慣れたテンプレートやボイラープレートを準備した
- [ ] 充電器、延長コード、モバイルWi-Fiを用意した

### 企画終了時

- [ ] 課題・ユーザー・解決策を1文ずつで言える
- [ ] Must機能とデモ台本が決まっている
- [ ] 役割分担とリポジトリが決まっている

### 発表前

- [ ] デモが台本どおり最後まで動く
- [ ] 予備のデモ動画を撮影した
- [ ] 時間を計ってリハーサルを2回行った
- [ ] 想定質問への回答を準備した
- [ ] 提出物（リポジトリ、スライド、動画URL）を期限内に提出した

## 用語集

| 用語 | 意味 |
| --- | --- |
| MVP | Minimum Viable Product。価値を検証できる最小限の機能を持つプロダクト |
| モック | 見た目や挙動だけを再現した仮の実装 |
| ピッチ | 短時間でアイデアや製品を売り込む発表 |
| エレベーターピッチ | 30秒程度で要点を伝える説明 |
| ワオポイント | デモで聴衆が驚く・感心する瞬間 |
| MoSCoW法 | 機能を Must / Should / Could / Won't に分ける優先順位付け手法 |
| HMW | How Might We。課題を「どうすれば〜できるか」の問いに変える手法 |
| ペルソナ | 想定ユーザーを具体的な1人として描いた人物像 |
| ジャーニーマップ | ユーザーの行動・感情を時系列で可視化した図 |
| 機能凍結 | 新機能の追加を止め、安定化に専念する時点 |
| ボイラープレート | プロジェクト開始時に使い回す雛形コード |
| アイデアソン | アイデアと企画のみを競うイベント |
| メンター | 開発中に技術や企画の相談に乗るサポート役 |

## 出典と確認範囲

2026-11-17に以下の一次資料を確認しました。知識集全体の効果・時間配分・人数の最適値を検証したものではありません。

- [ASQ — Five Whys and Five Hows](https://asq.org/quality-resources/five-whys)：問いの回数は5回より少ない場合も多い場合もあると説明しています。本資料では、確認前の原因候補を確定原因と扱わない運用を加えています。
- [IDEO.org — How Might We](https://www.designkit.org/methods/how-might-we.html)：特定の解決策を含めず、複数の解決が可能で、広すぎない問いにする説明を確認しました。公式ページの推奨時間は60分であり、上表の10分は短縮した問い作りの例です。

大会の規則・配点・参加条件は、その大会の公式資料を別に確認してください。参考例にあるサービス名や手順は、課金・公開・外部連絡を行う許可ではありません。
