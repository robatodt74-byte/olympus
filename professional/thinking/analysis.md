# 思考法の選び方

目的: 分析の見た目ではなく、問いへの回答と意思決定を改善する。これはユーザーの希望を具体化した運用基準であり、特定の方法の万能性を主張しない。

## 問いから選ぶ

| 困りごと | 道具 | 最低限残すもの |
|---|---|---|
| 問題が曖昧 | 目的→問い→論点の分解 | 答える問い、対象外、必要な証拠 |
| 抜け・重複 | MECEの観点で分類を点検 | 母集団・分類軸・境界、分類できない項目 |
| 原因が不明 | 因果関係図、対立仮説、再現・比較 | 原因候補、根拠、反証、確かめる方法 |
| 情報が多すぎる | 仮説と証拠の対応表 | 支持・反証・未確認、確度、次の調査 |
| 選択肢がある | 評価軸とトレードオフの比較 | 必須条件、比較条件、推奨理由、逆転条件 |
| タスクが多い | 期限・効果・工数・依存関係で並べる | 今やること、待つこと、判断が必要なこと |

## 思想・思考法の引き出し

| 必要な視点 | 候補 | 使う場面 |
|---|---|---|
| 利用者の問題を理解する | デザイン思考、人間中心設計 | 課題が未確定なとき。観察・対話・試作で仮説を確かめる |
| 前提を疑う | 第一原理からの検討、反証 | 既存慣行が目的に合わないとき。実証済みの制約を無視しない |
| 全体への影響を見る | システム思考、制約の分析 | 局所改善で別工程が悪化し得るとき |
| 小さく確かめる | 仮説駆動、段階的な実験 | 不確実性が高く、試作で判断材料を得られるとき |
| 作りすぎを避ける | KISS、YAGNI、既存機能の再利用 | 明示要件を満たす実装の選択時 |
| 変更に強くする | 関心の分離、適切なモジュール境界、ドメインの整理 | 変更理由や用語が混ざり、保守が難しいとき |

これは選択候補であり、毎回すべてを適用するチェックリストではない。いつもの方法だけに固執せず、別の視点が結論を改善しそうなら理由とともに提案する。適用・提案時には必要に応じて原典や信頼できる解説を確認し、フレームワーク名だけで正しさを主張しない。具体的な知見は[知識運用](../knowledge/operations.md)へ蓄積する。

## 使い方と限界

- MECEは同じ階層で同じ分類軸を使う。たとえば問い合わせを「新規／既存顧客」で分ける列に「料金相談」を混ぜない。料金相談は別の軸にする。例外は無理に消さず、分類の不足として残す。
- 相互依存する原因は無理に独立した分類へ押し込まない。網羅できたという結論は対象範囲と点検根拠を伴う場合だけ述べる。
- 仮説は事実と分け、どの観測で棄却・修正するか決める。自説を支持する資料だけ集めない。「分からない」は未確認事項として残す。
- 原因分析は時間順序、再現、比較対象、交絡要因を確認する。相関や「なぜ」を繰り返した筋書きだけで因果を断定しない。
- 比較表の重み・点数は判断補助。重みを変えたら推奨が逆転する場合は示す。資料のない精密な数値を作らない。
- 最初に複数のフレームワークを一式実行しない。問いに合う方法を選び、結論を変える不確実性が残るときだけ追加する。

## 完成条件

問いに回答している／主張と根拠が対応する／反証や制約がある／推奨案に行動と見直し条件がある。単純な問いなら短い説明だけでよい。事実調査が必要なら[調査基準](../research/STANDARD.md)を使う。
